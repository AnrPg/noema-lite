# noema-lite — content specification (any subject)

This is the contract between the **study engine** (subject-agnostic) and a **subject pack**.
Claude follows it when ingesting new sources; `tools/validate.py` enforces it; `tools/build.py` packs it.

## Repository layout of one subject
```
library/subjects/<subject-id>/          (shared library)   or   accounts/<profile>/packs/<subject-id>/   (private)
├── subject.json      identity + settings (below)
├── sources.json      the sources (PDFs, links…) in chronological order; maps chapter & patch files to sources
├── sources/          the original files (PDFs…) — archived, never published to the website
├── chapters/chNN.json   one file per chapter (schema below)
├── patches/*.json    ADDITIVE updates from later sources (never edit a published chapter; append)
├── media/            pictures (svg/png/jpg/webp) + media.json registry — docs/VISUAL.md
├── coverage/*.md     coverage checklists (every heading/command/test question → section + exercise ids)
├── authoring/        scripts used to generate the content (provenance)
├── translations/<locale>/chNN.json   OPTIONAL: the chapters in another language (below, "Packs in several languages")
└── pack.js / pack.json   GENERATED by tools/build.py (do not edit)
```

## subject.json
```json
{ "id": "cell-biology", "title": "Cell Biology", "appTitle": "Cell Biology Quest", "emoji": "🧬",
  "group": "life-sciences",                   // one of library/groups.json
  "description": "One line for the picker.", "language": "en",   // language of the material (tutor replies in it)
  "features": { "math": false, "code": false },                  // math → KaTeX; code → code highlighting & 'write' tasks
  "hero": { "headline": "Master **Cell Biology**, one bite at a time.", "mantra": "The one-sentence mental model." },
  "searchExamples": "mitosis, ATP synthase, p53",
  "tutor": { "name": "Brick", "avatar": "🦉", "domain": "cell biology",
             "prior": "What the learner already knows for THIS subject.",
             "examples": "Concrete examples to use (e.g. a liver cell under stress).",
             "interviewer": "an examiner for a cell biology oral exam",
             "simulation": "an experiment with an unexpected result, a patient case…",
             "terminology": "\"ATP synthase\", \"G1/S checkpoint\"", "examinerRole": "cell biology examiner" } }
```
The learner's personal profile ("About me") lives in the account, not in the subject.
`language` is the language the material is written in (BCP 47: `en`, `el`, `de`, `pt-BR` …; default `en`). Optional `i18n`:
the subject's name and description in other languages — see "Packs in several languages" at the end.

## sources.json
```json
{ "sources": [ { "id": "part2", "title": "…", "short": "ECB 2", "subtitle": "…", "pages": "403–569", "file": "sources/ecb_p403-569.pdf", "firstPage": 403, "url": "https://… (web sources)", "added": "YYYY-MM-DD", "emoji": "📘" } ],
  "chapters": { "ch01": "part1" }, "patches": { "ch11_links.json": "part2" } }
```
Every item inherits its chapter's source; patched-in items inherit the patch's source (or carry an explicit `"src"`).
This powers the in-app Sources menu, "✨ what's new" and source filtering. One entry per file (each part of a split PDF is its
own source), web page, video or conversation.

**The original files travel with the pack.** A file-based source has `"file": "sources/<file name>"` and that file is in the
subject's `sources/` folder — exactly the file the chapters were written from (for a split PDF: the part, never also the
unsplit original). `make_pack.py` (skill) packages them into `<id>.noema.zip` (`pack.json` + `sources/…`) and records for each
`fileName`, `size`, `sha256`, `mime` and, for PDFs, `pageCount`; it refuses a source without its file, a file without a source,
(any size: big files are stored in parts and joined again by the app; `scripts/split_pdf.py` only if you WANT one source per part). `firstPage` (default 1) is the page number the chapters cite for the
file's first page — a part that starts at page 403 of the book has `"firstPage": 403`, so "σ. 410" opens page 8 of the part.
The app imports the package with its files (📥, "Create with Claude", or the connector's `noema_finish_upload`, which asks for
every packaged file); files can also be attached later in the app (📎 in the source's card).

## Pedagogy rules (non-negotiable)
> **0. ADHD-friendly, everywhere — the first rule, it shapes every block, card and exercise.** Paragraphs of 1–3 short
> sentences; **one idea per block**; a concrete example or analogy for every abstract idea; lists and tables instead of
> long prose; a `reveal` "think first" prompt before the key point; a `hook` that says why the section matters; short
> question stems; no walls of text (a block over ~60 words is split). Read every section back as a tired learner would:
> if the eye cannot find the point in a few seconds, rewrite it.

1. **Coverage**: teach AND test every concept, number, caveat, trap, worked example and test question of the sources. Repeated material is taught once (best version). Every source exercise/test question becomes ≥1 exercise with its solution as the explanation.
2. **Diagnostic thinking first**: wherever the source describes failures, errors, anomalies, misconceptions, differential diagnoses or "first thing to check", build a `debug` playbook with an ordered `askYourself` list (first-person questions), an `ask` block in the section, ≥1 `scenario` and ≥1 `order` exercise. Long playbooks get a `mnemonic`.
3. **Pitfalls / exam traps** → callout (pitfall/exam/warn) + chapter `pitfalls` entry + ≥1 exercise tagged pitfall/exam.
4. **Co-location**: related concepts in the same section; comparisons side by side (`compare`/`table`); each exercise attached to its section; 2–4 `quick` exercises per section.
5. **ADHD-friendly**: see rule 0 above — it applies to every rule here.
6. **Accuracy**: faithful to the sources; correct clear errors (and say so in the coverage notes); no invented facts.
7. Diagrams redrawn cleanly (≤70 chars wide). Explanations teach (why right + why the tempting wrong answer is wrong). Every exercise type used several times per chapter.
8. **Visual learning (docs/VISUAL.md §5–6) — only pictures with high teaching value.** A picture is used only when it teaches something the text alone cannot (where things are, what they look like, how they connect, how a quantity behaves); **no picture is better than a decorative or weak one**, and pictures are never added to meet a count. Look for them in three places: (a) the pictures of the sources (`tools/extract_images.py`), (b) the web — high-quality, information-rich photographs and diagrams, any licence for personal study, always with the source recorded (`tools/fetch_image.py`), (c) redrawn diagrams and **function graphs** where the subject has them (`tools/svgkit.py`). Verify each picture is correct, relevant and sharp. **Every picture gets ≥ 3 exercises of ≥ 2 visual types** and a `figure`; a chapter that has pictures has ≥ 3 visual exercises and every picture exercise type ≥ 3 times (tools/pack_rules.json). A chapter without a picture that teaches has none. Enforced by `"authoring": {"minVisualPerChapter": 3, "minExercisesPerPicture": 3, "minPerKind": 3}`.

## Quality rules Q1–Q8 (binding for every chapter Claude or Gemini writes)
The learner never reads the sources. The app is the only place they learn from, so every lesson and exercise must stand
on its own and train real understanding. Lineage stays, but as data, not as text the learner must decode.

**Q1 · Self-contained.** No exercise, card, playbook or theory block points at the structure of a source: no question
numbers ("Q2", "Round 1 Q14", "Exercise 3"), no pages / paragraphs / sections ("p. 1", "σ. 23", "§2"), no "the source",
"the author", "the conversation", "the example dataset on p. 1", "in the order the source lists them". When a source
example or question is needed, **write it out in full** in the exercise (`q`, `code`, a table in the theory). Where it
came from goes in `cite` (below) and in the chapter's `sources`; the app shows it as a small chip **after** the answer.
- ✗ "What was the bug in Q2?" → ✓ the Q2 code itself in `code`, then "Which line makes this query return duplicates?"
- ✗ "Complete the Round 1 Q15 answer." → ✓ "Parquet is a file format. Which three guarantees does it **not** give by itself?"
- ✗ "Put the distinctions in the order the source lists them." → order only what has a real order (a process, a lifecycle).

**Q2 · Every question of the sources, answered and checked.** List every question / problem / exercise of the sources in
the chapter's map (`sourceQuestions`). Each becomes ≥ 1 exercise with its full text (verbatim, or completed with what it
silently assumes) and `cite.sq` = its id in the map. Solve it twice, independently, and compare with each other and with
the source's answer; recompute numbers with a script; run code / SQL where you can. A wrong source answer is corrected,
and the explanation says so.

**Q3 · Knowledge map first** (`map/chNN.json`, below). Write it before the chapter; every exercise names its learnable
(`lr`); every source question and every point of the pages is in it.

**Q4 · From the foundations up.** Per chapter, difficulty 1 / 2 / 3 ≈ **20 / 25 / 55 %** (±5). Inside each section the
exercises go from easy to hard. Foundations are never skipped: every learnable of the map is taught and tested, not only the
hard ones.

**Q5 · Fewer trivial exercises.** Every exercise states its kind of thinking in `think`: `recall`, `explain`, `apply`,
`discriminate`, `analyze`, `evaluate` or `create`. Per chapter `recall` ≤ 25 % and `apply` or higher ≥ 40 %. Trivial =
the answer is in the prompt; the right option stands out (longest, the only one without "always" / "never"); no one would
pick the distractors (distractors must be real misconceptions); a `tf` that copies a theory sentence; a one-word answer
that needs no thinking. Keep a few easy ones, make most of them make the learner think.

**Q6 · The hard categories, exhaustively — on top of the basics.** Every learnable the map tags with a category (below)
gets ≥ 2 exercises of different types and its own treatment in the theory (`compare` side by side for confusables, `flow`
for sequences, `terms` for acronyms and nomenclature, a callout for traps and edge cases, a `mnemonic` for what is hard to
remember).

**Q7 · Theory of high value.** Each section: hook → the basic idea → the mechanism (why) → a self-contained example →
contrast with what it is confused with → edge cases → a `reveal` "think first". Every acronym is expanded at first use and
listed in a `terms` block. Never "the source says".

**Q8 · Explanations that teach, answers that were checked.** `explain` says why the right answer is right **and** why the
tempting wrong one is wrong (≥ 2 sentences); every `mcq` has `why` for every option. After writing, **solve blind**: answer
every exercise without looking at its key; fix or rewrite every one where you disagree with the key or found it ambiguous.
Then **review** a sample (below).

### One learnable, many facades
Several exercises may test the same learnable in different types — the same fact as an `mcq`, a `tf`, a `calc`, a `cloze`.
This is wanted: write the learnables first, then the facades. Roughly 300 exercises per chapter is a good size; it is a
**mild suggestion**, never a hard limit (the checker only warns).

### Coverage that must hold in every chapter
- every exercise type that fits the chapter (the map's `fits.types`) — about 3 or more each;
- every focus that makes sense (`tags` and the map's categories);
- `think`: recall ≤ 25 %, apply or higher ≥ 40 %;
- difficulty ≈ 20 / 25 / 55 %;
- most (ideally all) learning paradigms that fit (`fits.modes`) in ≥ 2 exercises each (`mode`, below).

### Learning paradigms (`mode`) — with the existing exercise types
| `mode` | what the learner does | typical types |
|---|---|---|
| `contradiction` | two right-looking statements that cannot both hold: which premise breaks, which principle resolves it | mcq, free |
| `reverse` | given the answer / output, find the question / input | mcq, write |
| `whatif` | "what changes if X were different?" (counterfactual) | mcq, scenario |
| `perturb` | a small change of a parameter: predict the effect | calc, mcq |
| `causal` | fill the missing steps of a chain of reasoning | cloze with bank, order |
| `distinguish` | sort descriptions between 2–3 confusable concepts | bucket, odd |
| `translate` | code ↔ words ↔ diagram ↔ formula | match, write, img_* |
| `ambiguity` | an under-specified problem: which clarifying question first | scenario |
| `feynman` | explain it to a beginner / a child | free (audience in the rubric) |
| `combine` | connect two concepts from different chapters | free, mcq |
| `dialectic` | a thesis and a critique: find the synthesis ("when each holds") | mcq, free |

### The knowledge map — `map/chNN.json` (written before the chapter)
`points` is the exhaustive inventory: **every** knowledge point and concept of the chapter's pages, never a selection. A
point an earlier step of the Roadmap already taught carries `taughtIn` and is not taught again; every other point sits in
some learnable's `kp`.
```json
{ "format": "noema.map/v1", "chapter": "ch03",
  "points": [ { "id": "ch03-k07", "text": "MERGE fails when several source rows match one target row", "level": "core",
                "cats": ["pitfall", "edge"], "cite": {"src": "ecb", "loc": "p. 41"} },
              { "id": "ch03-k08", "text": "DELETE vs TRUNCATE: TRUNCATE keeps no per-row history", "level": "foundation",
                "cats": ["confusable"], "with": ["ch03-k09"], "cite": {"src": "ecb", "loc": "p. 44"} },
              { "id": "ch03-k02", "text": "The Delta transaction log", "level": "foundation", "cite": {"src": "ecb", "loc": "p. 40"},
                "taughtIn": "<earlier node or chapter id>" } ],
  "learnables": [ { "id": "ch03-l01", "kp": ["ch03-k07"], "goal": "Predict and fix a MERGE that matches several rows" } ],
  "fits": { "types": ["mcq", "tf", "cloze", "write", "spotbug", "scenario", "order", "match"],
            "focus": ["concept", "syntax", "pitfall", "debug", "compare"],
            "modes": ["contradiction", "reverse", "whatif", "causal", "distinguish", "translate"] },
  "unfit": { "dialectic": "pure syntax, nothing to argue" },
  "sourceQuestions": [ { "id": "ch03-q01", "text": "full text…", "answer": "checked solution…", "cite": {"src": "r1", "loc": "Q14"} } ] }
```
- `level` ∈ foundation · core · advanced (the order of the sections follows it).
- `cats` ⊂ pitfall · confusable · falsefriend · detail · sequence · multipart · nomenclature · acronym · formula · edge ·
  recent · hard-understand · hard-remember; `with` names the other point(s) of a confusable / false-friend pair.
- Every exercise type, focus tag and mode is either in `fits` or has a reason in `unfit`.
- Steps: (1) list every point of the pages; (2) one pass per category; (3) list the source questions; (4) group the points
  into learnables, foundation → advanced; (5) decide what fits; (6) plan the facades of every learnable.

### Fields this adds to an exercise
`lr` (the learnable it tests — required), `think` ∈ recall · explain · apply · discriminate · analyze · evaluate · create,
`mode` (optional, the ids above), `cite` `{ "src": "<source id>", "loc": "p. 41", "sq": "ch03-q01" }` — lineage, shown only
after answering, never in the text; `sq` names the source question the exercise reproduces (each one needs ≥ 1).

### Mix per chapter (checked)
recall ≤ 25 %; apply or higher (apply, discriminate, analyze, evaluate, create) ≥ 40 %; analyze / evaluate / create ≥ 3;
difficulty 20 / 25 / 55 % (±5); every learnable and every categorised point ≥ 2 exercises of ≥ 2 types; every fitting
type and focus ≥ 3, every fitting mode ≥ 2. Exercise counts are only a mild note, never an error.

### The review — `review/chNN.json` (written after the blind solve)
```json
{ "format": "noema.review/v1", "chapter": "ch03",
  "rubric": [ { "lr": "ch03-l01", "ok": true, "notes": "distractor C was implausible — rewritten" } ],
  "blind": { "solved": 312, "mismatches": [ { "id": "ch03-e044", "fixed": true } ] } }
```
- `blind`: you answered every exercise without its key; every disagreement is listed and fixed (key corrected or the
  exercise rewritten until unambiguous).
- `rubric`: ≥ 15 learnables (all of them if fewer) checked for self-containment, depth, real distractors and teaching
  explanations; whatever falls short is rewritten. If you can start a sub-agent, let one that has not read the sources do it.
- `make_pack.py` embeds the map and a summary of the review in the chapter (`chapter.map`, `chapter.review`).

## Inline text format (all text fields)
`**bold**`, `*italic*`, `` `inline code` ``, and `\n` for a line break. No HTML.
Math (subjects with `features.math`): `$…$` inline, `$$…$$` display (KaTeX). Inside math write `\cdot` / `\times`, never a bare `*` (it would be read as italics).

## Blocks (`t` = type)
- `{"t":"p","text":"..."}`
- `{"t":"list","items":["...","..."],"ordered":false}`
- `{"t":"code","lang":"sql|python|bash|yaml|text","code":"multi\nline","caption":"optional"}`
- `{"t":"diagram","text":"ASCII art\nmulti-line","caption":"optional"}`
- `{"t":"table","head":["Axis","Options"],"rows":[["..",".."]],"caption":"optional"}`
- `{"t":"callout","kind":"key|pitfall|tip|exam|warn|analogy|debug|interview","title":"...","text":"..."}`
- `{"t":"compare","items":[{"title":"Classic","points":["..",".."]},{"title":"Serverless","points":[".."]}]}`  (2–3 items)
- `{"t":"flow","items":["READ","WRITE","VALIDATE","COMMIT"],"caption":"optional"}`   (a process chain, 2–9 short steps)
- `{"t":"reveal","label":"Think first: …?","text":"answer revealed on click"}`
- `{"t":"ask","title":"Ask yourself when … ","questions":["Am I …?","Did …?"]}`
- `{"t":"terms","items":[{"term":"Principal","def":"..."}]}`
- `{"t":"figure","media":"heart-frontal","caption":"optional"}` — an explorable picture (docs/VISUAL.md §4)

## Exercise — common fields
```json
{ "id": "ch05-e012", "type": "...", "section": "ch05-s03", "difficulty": 1, "tags": ["concept"],
  "quick": false, "q": "Prompt (inline format allowed)", "code": "optional code shown under the prompt",
  "explain": "Teaching explanation shown after answering." }
```
`tags` ⊂ {concept, syntax, pitfall, debug, exam, interview, calc, compare}.
Quality fields (Q1–Q8 above): `"lr": "ch05-l03"`, `"think": "apply"`, optional `"mode": "whatif"`, optional `"cite": {"src": "ecb", "loc": "p. 41", "sq": "ch05-q02"}`.
IDs: `chNN-eNNN`, unique, sequential.

### Types (extra fields)
| type | fields | notes |
|---|---|---|
| `mcq` | `options:[str]`, `answer:int` or `answer:[int,...]` + `"multi":true`, optional `why:[str per option]` | 3–5 options, plausible distractors; `why` strongly encouraged |
| `tf` | `answer:true/false` | `q` is a statement. Great for myths & traps. |
| `odd` | `options:[4 str]`, `answer:int` | "Which one doesn't belong?" — explain the grouping |
| `order` | `items:[str]` in the CORRECT order | 3–8 items; engine shuffles |
| `match` | `pairs:[[left,right],...]` | 3–6 pairs, rights must be distinct |
| `bucket` | `buckets:[str]` (2–4), `items:[{"text":..,"bucket":idx}]` | 5–10 items |
| `cloze` | `text` with blanks `[[answer|alt answer|alt]]`, `"bank":[distractors]` optional, `"asCode":true` for code | With `bank` → learner taps chips into blanks; without → types. First variant is canonical. Answers compared case-insensitively, whitespace-trimmed. |
| `spotbug` | `lines:[str]` (code lines), `bugs:[line indexes, 0-based]`, `fix:"corrected code or text"` | learner clicks the buggy line(s) |
| `calc` | `answer:number`, `tolerance:number`, `unit:"tasks"` | numeric reasoning |
| `scenario` | `steps:[{"prompt":..,"code":opt,"options":[{"text":..,"ok":true/false,"fb":"feedback"}]}]` | debugging simulations: each step = "what do you check/do next?". 2–5 steps, exactly one ok per step, every option has `fb`. |
| `free` | `model:"model answer"`, `rubric:["key point",...]` | explain-in-your-own-words / interview answers. Graded by Gemini or self-check. |
| `write` | `solution:"code"`, `keywords:["merge into","when matched",...]`, `lang` | learner writes real syntax; local check = all keywords present (case-insensitive substring) |
| `img_hotspot` `img_sequence` `img_reveal` `img_drag` `img_label` `img_select` `img_occlusion` | `media` + regions/targets/answer… | **visual exercises — full schema in docs/VISUAL.md** |

## Quantity guide
Enforced per chapter by `tools/pack_rules.json` (one rule list, read by `validate.py` / `make_pack.py` / `build.py` and by
`engine/packcheck.js` for the app, the Gemini generator and the connector's `noema_finish_upload`):
* **every exercise type ≥ 3 times**: `mcq tf odd order match bucket cloze scenario free` always; `spotbug write` when
  `features.code`; `calc` when `features.math`; the 7 picture types when the chapter has a picture (rule 8);
* **every difficulty** 1, 2 and 3 **≥ 3 times**;
* **every focus tag ≥ 3 times**: `concept pitfall debug exam interview compare` always; `syntax` with code, `calc` with math;
* an optional type or tag the chapter uses anyway needs 3 too. `subject.authoring.minPerKind` (3, written by
  `start_subject.py`) sets the number; packs made before 2026-10-21 have none and get warnings; chapters of such a pack
  that is being extended (`unpack.py`) warn, new chapters must pass.
Also: ≥ 5 exercises per section, ≥ 2 quick ones each; ≥ 30% of exercises tagged `pitfall`, `debug` or `exam`.
Be exhaustive rather than brief: depth and coverage beat polish.

## Also produce
`chNN.coverage.md`: a checklist of EVERY numbered heading / concept / command / test question in your page range →
the section id and exercise ids that cover it. Use it to self-audit before finishing; add anything missing.


## Additive updates (new sources for an existing subject)
* Never edit or delete published chapter files — progress and SRS schedules are keyed by section/exercise/flashcard ids.
* New topics → new chapter files (next free `chNN`). Material for existing sections → a patch file in `patches/`:
```json
{"patches":[{"chapter":"ch02","section":"ch02-s05","appendBlocks":[…],"appendExercises":[…],"appendFlashcards":[…],"appendPitfalls":[…],"appendDebug":[…]}]}
```
  Patched exercise and flashcard ids must not collide: reserve a range per patch file (e.g. `chNN-e7NN`, `chNN-f7NN`); patch cards without an id get the next free one. Databricks: `e6NN` = visual_v1, `e7NN`–`e9NN` = the links patches.
  Typical patch content: a `callout` (kind key/tip, title "Level-up → …") linking to the deeper new chapter, plus genuinely new nuances with an exercise each.
* Register the new source in `sources.json` (append; order = chronology) and map the new chapter/patch files to it.
* `python3 tools/build.py` validates the MERGED result; `python3 tools/db_sync.py` records the new version in the backup database.

## Validation
`python3 tools/validate.py FILE.json` (single chapter) — `python3 tools/build.py` (everything, merged with patches).

## Packs in several languages (optional — pack schema v2, additive)
A pack is written in ONE language (`subject.language`). It MAY also offer its metadata and, optionally, its chapters in
other languages; the learner sees them when the pack has their **interface language** (or its language: `es-ES` → `es`).
The interface language never changes content by itself: without a translation for it the learner sees the pack's own
texts, with a small language tag (e.g. `EN`) beside the name. **Never required** — add translations only when the user
asks for them (e.g. a Greek class using an English pack). Locale codes: the app's UI locales `el ru fr de it es-ES pt-PT
sq tr ar-EG hi ja zh-Hans zh-Hant en`, or a bare language (`es`, `pt`, `ar`) that covers its regional ones.

**1. Metadata** — `subject.json` → `i18n`, one object per locale with any of `title`, `appTitle`, `description`,
`searchExamples`, `hero` {`headline`, `mantra`}, `tutor` {any of the subject's own tutor keys, e.g. `domain`, `examples`}.
Only fields the subject itself has; a missing field shows the source text. Shown in the subject picker, the Shelf,
Explore, shared/public packs and on the subject's home.
```json
"language": "en",
"i18n": { "el": { "title": "Κυτταρική Βιολογία", "description": "Μία γραμμή για τον κατάλογο.", "hero": { "headline": "Κατάκτησε την **Κυτταρική Βιολογία**." } },
          "fr": { "title": "Biologie cellulaire", "description": "Une ligne pour le catalogue." } }
```
**2. Content (optional)** — `translations/<locale>/chNN.json`: the WHOLE chapter in that language, exactly as built
(base chapter + its patches), with **the same ids, the same sections and blocks in the same order, the same exercises,
playbooks, flashcards and pitfalls, the same answers** (option order, answer indexes, buckets, bug lines, picture regions,
`targets`, `media`) — only the words change (titles, texts, questions, options, explanations, cards, cloze answers).
Progress, spaced repetition and sources are keyed by the ids, so they are shared between the languages. A chapter without
a translation is shown in the pack's language. Labels drawn on a picture come from `media/media.json` (one language): a
translated `img_drag` / `img_label` / `img_select` exercise may carry its own `regions` with translated labels.
When a later patch adds items to a translated chapter, add them to every `translations/<locale>/chNN.json` too (the
validator refuses a translation with missing ids). Add `subject.i18n.<locale>` too, so the picker shows the translated name.

**Built pack** (`tools/build.py`, `make_pack.py`): `"v": 2` when the pack has `subject.i18n` or translations (older apps
ignore both and show the source), and `"translations": { "<locale>": { "chapters": [ … ] } }` beside `"chapters"`.
**Validation**: `python3 tools/validate.py subject.json --subject [--translations el,fr]` (locale codes, known fields,
only what the source has) and `python3 tools/validate.py translations/el/ch03.json --source ch03.json` (the same ids,
structure and answers as the built source chapter); both run inside `build.py` and `make_pack.py`.

## Language help for learners of another language (文A bridges — optional, a sidecar)
A pack in one language can also get **bridges**: its content words, in the meaning they have in the pack, translated into
a learner's native language, with each section's key words and a short preview. They live beside the pack
(`bridges/core.json` + `bridges/<native>.json`), never inside it, and are made with `tools/bridge.py` — the format, the
rules and the workflow are in docs/BRIDGE.md (in the skill: `references/BRIDGE.md`). Not part of a pack's validation;
only when the user asks.
