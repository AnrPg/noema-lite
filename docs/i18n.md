# 🌐 Internationalization (i18n) and localization (l10n)

Status: **plan accepted 2026-10-11 — Wave 0 in progress** (branch `i18n`). This file is the contract for every text a
learner reads in the app. It grows with each wave; the language courses' own architecture (core + facades) is
`docs/language-packs.md`.

## 1. Four languages that are never the same thing

| | What | Where it is stored | Default |
|---|---|---|---|
| **UI language** | the app's chrome: buttons, menus, settings, messages | `a:settings.lang` (account, synced, in backups; Arabic digits: `a:settings.numerals` = `arab` \| `latn`) | the device's language if supported, else `en` (asked once to confirm) |
| **Speaker language** (explanation locale) | the language a course or pack is explained in | language courses: per course, `s:lang:<course>:settings.speaker` — an override, changeable any time; without it the course follows D19 (docs/language-packs.md §2.2); subject packs: `subject.language`, chosen at creation (default `en`) | language courses (D19): the learner's **native language** if it is a supported locale and the course's facade for it is on, else the UI language (if its facade is on), else `en`; comparisons only with the native language (or its type / branch / family) |
| **Learned languages** | what the language module teaches | `s:lang:<course>:settings.languages` | the course's languages |
| **Native language** (D19) | the learner's mother tongue: it decides the explanation locale of language courses and comes first among the languages they are compared with (R1, 2026-10-11: “From your languages” = the native, then the languages spoken at C1 / C2 in `settings.knows`; then “Among the languages you are learning”; then “From other languages”, folded) | `a:settings.native` (`{code}` or `{name, type, family, branch}` for a language that is not supported); fallback: the course's `settings.knows` entry with level `native` | asked once by a language course ("Your native language?"); until then only type-free general texts, no notes |

The UI language never changes a pack's or course's content, and the other way round — except that a language course
explains itself in the UI language to a learner whose native language is not a supported locale (D19). Learned languages are open-ended
(Hebrew is learned, but is not a UI locale).

## 5. How to write a translatable text (the rules every change follows)

### 5.1 Components, keys, files

| Component (`i18n/<c>/`) | Code | Key prefix |
|---|---|---|
| `core` | shared by `engine/src/*` (`t()`) and `engine/loader.js` (`tr()`) — the keys migrated from the old bundles | `pick.` `set.` `acc.` … (as they are) |
| `shell` | `engine/shell.js` (`L()`, prefix added by `L`) | `sh.` |
| `engine` | `engine/src/*.js` | `engine.` |
| `loader` | `engine/loader.js`, `react.js`, `convos.js`, `viewer.js`, `imglib.js`, `index.html` | `loader.` |
| `roadmaps` | `curmap.js`, `curriculum.js`, `curshare.js`, `curjobs.js`, `curimport.js`, `packgen.js`, `packcheck.js` | `roadmap.` |
| `characters` | `themes.js`, `art.js` | `char.` |
| `lang` | `engine/lang/*.js` (the language module's UI) | `lang.` |
| `langcore` | `engine/langcore.js` (exercise words and labels generated at run time) | `lc.` |
| `errors` | `cloud.js`, `srcfiles.js`, `claude.js`, `llm.js`, `cloud/img/proxy.mjs`, error codes of the backend | `err.` |
| `email` | `cloud/email/*` (Supabase auth e-mails) | `email.` |
| `packs` | subject packs in several languages (§10): the language tag of `engine/loader.js` | `packs.` |

* Keys are semantic and dotted: `engine.notif.empty`, `roadmap.step.markDone` — never the English text, never reused for a
  different meaning (the same English word in two places = two keys if a language could say them differently).
* Every English key has a description for translators: where it appears, what the placeholders are, length limits
  (`"@engine.notif.empty": {"description": "Notifications panel when there is nothing new. Short.", "placeholders": {…}}`).
* Keys built at run time (`'sh.dom_' + id`) are listed in `i18n/<c>/dynamic_keys.txt` (a key or `prefix*` per line).
* Only `en.arb` is written by hand. Claude's translations go to `drafts/<locale>.arb` (imported into Weblate as *needs
  editing*); `<locale>.arb` is written by Weblate only (and once by the migration of the old bundles).
* Generated, never edited: `engine/i18n/*.js` (`node tools/i18n/build.js`, run by `tools/build.py`).

### 5.2 In the code

```js
const T = (k, p) => window.NoemaI18n ? NoemaI18n.t(k, p) : k;          // per file (engine/src has t(), loader tr(), shell L())
toast('✅ ' + T('engine.saved', { title }));                             // a leading decorative emoji may stay outside
T('roadmap.steps', { n: steps.length })                                  // "{n, plural, one {# step} other {# steps}}"
NoemaI18n.fmt.date(ts) · fmt.number(x) · fmt.percent(r) · fmt.ago(ts) · fmt.list(names) · fmt.compare(a, b)
```

* **A whole sentence is one message.** No `'You have ' + n + ' cards'`, no sentence glued from pieces, no `n === 1 ? … : …`
  (ICU plural), no English word order in code. A bold part: a placeholder filled with an element (`rich()` in shell.js).
* **Plurals** `{n, plural, one {# card} other {# cards}}` (`#` prints the number in the locale's digits); a bare `{n}`
  is not number-formatted — write `{n, number}`. Choices: `{kind, select, pack {…} roadmap {…} other {…}}`.
* **Apostrophes**: write ’ (U+2019) in messages; an ASCII `'` before `{` `}` `#` starts ICU quoting (`check.js` refuses it).
* **Numbers, dates, lists, sorting** only through `NoemaI18n.fmt` (never `toLocaleString()` without the UI locale,
  never `a.localeCompare(b)` without it).
* **Not for learners → mark it**: `// i18n-ignore` on the line, `/* i18n-ignore-start */ … /* i18n-ignore-end */` around
  a block: prompts for the AI (approach 6: written in English, they *ask* for the learner's language), logs, test hooks,
  sample text in a learned language, CSS/SVG.
* **English stays word for word** what it was (the tests read it); a better English text is a separate, explicit change.
* **Errors**: a message a learner reads is translated where it is shown. The backend answers
  `{ error: { code: 'img.too_large', params: { max: 10 }, message: '<English, for old clients>' } }`; the app shows
  `T('err.' + code, params)` and falls back to `message` (§6).
* **RTL**: CSS logical properties (`margin-inline-start`, `inset-inline-end`, `text-align: start`); user and course text
  inside an RTL page gets `dir="auto"`; icons that point (← →) are mirrored with `:dir(rtl)`.

### 5.3 Checks (CI: `bash tests/run_e2e.sh` runs them)

* `node tools/i18n/check.js` — ICU syntax, placeholders equal to English, CLDR plural categories per locale (ru: one/few/
  many/other; ar: zero/one/two/few/many/other), keys not in English, keys missing in a locale that is on, apostrophes,
  descriptions; sensitive keys (`"x-sensitive": true`: legal, billing, safety) never shipped as drafts.
* `node tools/i18n/audit.js --diff main` — no new hard-coded learner text in the lines a change adds.
* `node tests/i18n.js` — runtime: chains, plurals in ru/ar/fr/ja, digits, pseudo-locales, missing keys, error codes.
* `node tests/i18n_runtime.js <prepared-repo>` — the runtime audit: the app in the pseudo-locale `en-XA` (every catalog text
  accented and bracketed), every surface visited (classic engine, the frame, Roadmaps, the language course, cloud sign-in
  and its errors, sharing, the OAuth consent page, Create with Claude with the API's errors, dialogs, toasts, `title` /
  `aria-label` / `placeholder` / `alt`); it fails on any plain Latin text that is not content (the packs and courses,
  the course's explanation-language texts `lang.expl.*` / `lc.expl.*`), user data, a product name or a code. Then `ar-XB`:
  key pages right to left, screenshots, nothing scrolling sideways. `I18N_ONLY=BC`, `I18N_DEBUG=1`, `I18N_SHOTS_ALL=1`.

### 5.4 Data and codes, not words

Words change with the UI language; what the code decides must not depend on them.

* **Compare ids, never labels.** A value that code tests, matches, sorts by or uses as a map key is a stable id, not
  the words shown for it: langcore's principal parts are `[words, value, id]` and code compares `p[2]` (`'article'`,
  `'transliteration'`), never `p[0]`; a log entry says what it is in a field (`l.via === 'claude-app'`), not in its
  words (`startsWith('💬 Claude app')` stays only for entries written before); a button names its frame icon
  (`data-icon="gym"`) instead of having it guessed from its English label; tags, registers, kinds and statuses are
  looked up by their code (`lc.expl.reg.<register>`, `roadmap.map.kd.<domain>`), and a code the catalog does not know
  is shown as it is. No English grammar in code either: no `label + 's'` plurals, no `.split(' ')[0]` of a translated
  word — a message with `{pos, select, …}` or `{n, plural, …}` says it.
* **Store codes + params, translate where it is shown.** A text saved now and read later (perhaps on another device, in
  another UI language) keeps a code beside the words it was saved with — additive, so older apps still read the words:
  a restore point `{ label, k, p }` → `t(k, p)`; a job's or a Roadmap step's error `error` + `errorInfo { code, params }`
  → `NoemaI18n.err(errorInfo)`; a log entry `{ m, k, p }`; the “in use” row `{ name, os, br }`. Fixed names that code
  also matches (the daily cloud snapshot) are stored as one constant English name and mapped to a key where they are
  shown. Entries saved before keep showing their stored words; so does an entry whose code has no catalog entry.
* Language names: `NoemaI18n.fmt.langName(code)`, not an English table (English keeps the words it always showed).

## 6. Errors and e-mails

### 6.1 The error contract (version 1)

Every error a learner may read has a **stable code** (component `errors`, catalog `i18n/errors/`, key = `err.` + code).

* **In the app** a module throws an `Error` whose `.message` is the English text it always had (logs, older callers, the
  tool results Claude reads, regexes on messages keep working) plus `.code` and `.params`. Where it is shown:
  `NoemaI18n.err(e)` → `t('err.' + code, params)` in the UI language, or `e.message` when the code has no catalog entry
  (older servers, codes added later). **Show `NoemaI18n.err(e)`, never `e.message`.**
* **From a server** (`cloud/img/proxy.mjs`, later functions): a client that sends `Accept: application/json` gets
  `{ "error": { "code": "img.too_large", "params": { "max": 15 }, "message": "larger than 15 MB" } }`; any other client
  (older apps, scripts, `tools/fetch_image.py`) gets the English `message` as `text/plain`, as before. Both carry
  `x-error-code` and `x-error-params` (URI-encoded JSON), exposed to the browser.
* Texts the modules write themselves are already in the UI language, with what they were kept beside:
  `NoemaCloud.status()` → `error` (words) + `errorInfo` `{ code, params, message }`; a “Create with Claude” job →
  `job.error` + `job.errorInfo`; the cloud self-check → each failed step's `error` + `errorInfo`; the progress log lines.
* **Rules.** A code is never renamed, removed or reused for another meaning; params may be added, never removed or
  retyped; the English message of a code stays the same (the test `tests/i18n_errors.js` checks
  `t('err.' + code, params, 'en') === e.message` for every code it provokes, and that this table lists every code).
  Exception, marked *server's words* below: a code that classifies a server's answer keeps the server's own text in
  `.message` (unchanged, for logs and older callers); the catalog has our words for it.
  A breaking change gets a new code (and, for servers, `v2` here). Params hold raw values (numbers, English technical
  details) — `detail` is the provider's or browser's own words and stays as it is.

### 6.4 The account e-mails (Supabase Auth)

`cloud/email/<template>.html` (the body) and `<template>.subject.txt` (the subject), one per e-mail Supabase sends:
`confirm-signup` (Confirm signup), `invite` (Invite user), `magic-link` (Magic Link), `change-email` (Change Email Address),
`reset-password` (Reset Password), `reauthentication` (Reauthentication). **Generated, never edited**:
`node tools/i18n/emails.js` from `i18n/email/<locale>.arb` (keys `email.<template>.*`, `email.common.*`).

* Every language is in the one template, chosen by the account's locale (Supabase exposes `user_metadata` as `.Data`):
  `{{ $l := printf "%v" .Data.locale }}{{ if eq $l "el" }} … {{ else if eq $l "ru" }} … {{ else }} English {{ end }}` —
  `printf` turns a missing locale into a string, so accounts made before §6.3 get English and `eq` never compares nil.
  A regional tag also matches its bare language (`es-ES` ← `es`), never across scripts (zh-Hans / zh-Hant).
* **Only reviewed translations** (`i18n/email/<locale>.arb`, written by Weblate) reach the production templates; a locale
  gets its branch in a template only when every key of that template is translated (never two languages in one e-mail).
  Until then production is English only. `--drafts` writes the **preview set** `cloud/email/preview/` with Claude's drafts
  (el, ru, fr) for review — not for production. `--check` fails when `cloud/email/` is not what the catalogs give.
* **Subjects**: Supabase's mailer runs the subject through the same Go template engine with the same data (supabase/auth,
  `internal/mailer/templatemailer`), so the subject branches the same way. If the dashboard ever refused a templated

* Supabase's variables used: `{{ .ConfirmationURL }}`, `{{ .Email }}`, `{{ .NewEmail }}`, `{{ .Token }}`, `{{ .Data }}`.
  ICU placeholders map to them: `{email}`, `{newEmail}`, `{token}`, `{siteUrl}`.

**Deploy note (by hand, nothing is deployed by the repo).** After `node tools/i18n/emails.js`: Supabase dashboard →
the project → Authentication → Emails (Templates) → for each of the six e-mails, paste `<template>.subject.txt` into
*Subject* and `<template>.html` into *Message body* (Source), Save. Then send yourself one (e.g. Reset password from the app)

for templates, but Supabase's built-in mailer only sends to the project's team addresses and a few e-mails per hour.

## 9. Weblate — the translation platform

Decision (owner, 2026-10-11): **Weblate, self-hosted on the owner's server, designed in from day one.** Until that
server exists it runs on a small container host with **Supabase as its PostgreSQL** (Weblate is Django + Celery +
PostgreSQL + Redis with Git checkouts on a disk: Netlify — static files and short-lived functions — and Supabase —
Postgres and Edge Functions — cannot run it; Supabase *can* be its database). Hosting options compared, first start,
backups, upgrades and the later move: **`weblate/README.md`**. Nothing is deployed by the repository.

### 9.1 Who edits what

| File | Written by | How it changes |
|---|---|---|
| `i18n/<c>/en.arb` (source + descriptions) | developers and agents, in the repo | a normal pull request; Weblate never edits English (`edit_template: false`, `manage_units: false`) |
| `i18n/<c>/<locale>.arb` (approved translations) | **Weblate only** | Weblate's pull request `weblate-translations → main`, merged by the owner. Nobody edits it by hand (exceptions: the one-time migration of the shipped bundles, a revert, `init-locale` stubs) |
| `i18n/<c>/drafts/<locale>.arb` | Claude (agents), in the repo | imported into Weblate as *needs editing*; pruned once approved (§9.3) |
| `i18n/glossary/terms.csv` | the repo | the English term list |
| `i18n/glossary/<locale>.csv` | Weblate (glossary component) | like the catalogs; `drafts/<locale>.csv` like the ARB drafts |
| `library/languages/<course>/facades/<locale>/*.json` | Claude (`lang_facade.py merge`, `by: "claude"`) and Weblate (`weblate_facades.py import`, `by: "weblate"`) | §9.4 |
| `config.js` `locales` | the owner | §9.5 |

### 9.2 Projects, components, checks (configuration as code)

`weblate/components.yaml`, applied idempotently by `python3 tools/i18n/weblate_setup.py apply [--apply]` (a dry run
that only reads unless `--apply`; it creates and patches, never deletes):

* **Project `noema-lite`** (private, reviews on, commit policy **"Only include approved translations"**):
  one component per `i18n/<component>/` with an `en.arb` — file format *ARB*, monolingual, template
  `i18n/<c>/en.arb`, file mask `i18n/<c>/*.arb` (the `drafts/` subfolder never matches), BCP 47 file names
  (`language_code_style: bcp` → `zh-Hans.arb`, `pt-PT.arb`), ICU MessageFormat check on and **enforced**
  (syntax, placeholders equal to English, `other` in every plural / select). `core` holds the Git repository; the
  others link to it (`weblate://noema-lite/core`): one clone, one push branch, one pull request. Add-ons on `core`:
  *Squash Git commits* (one commit per language, co-author trailers kept) and *Cleanup translation files* (keys
  removed from `en.arb` disappear from the translations). Plus the **glossary** component (`i18n/glossary/*.csv`,
  `terms.csv` excluded; bilingual CSV `source,target,developer_comments` — the column name translate-toolkit keeps:
  one called `description` would be written back empty, so `weblate_setup.py` leaves the component out while any
  glossary CSV still has it; `tools/lang_facade.py glossary()` reads `developer_comments` and, for older files,
  `description`).
* **Project `noema-lite-courses`** (same policies): the language-course facades, §9.4.
* **Git**: VCS *GitHub pull request*, SSH repository URL (Weblate's SSH key is a deploy key with write access on the
  private repository), **push branch `weblate-translations`**, pull requests to `main` opened with a fine-grained
  token (`WEBLATE_GITHUB_TOKEN`, only on the server). Changes are committed at least daily (`commit_pending_age: 24`)
  or by hand (Repository maintenance → Commit).
* **Webhook GitHub → Weblate**: repository → Settings → Webhooks → `https://<weblate>/hooks/github/`, JSON, push
  events (`weblate_setup.py webhook` prints it). Weblate matches the delivery by **exact repository URL**: the
  components keep the SSH URL `git@github.com:<owner>/noema-lite.git`.
* **New locale**: `python3 tools/i18n/weblate_setup.py init-locale <tag> --write` writes `{"@@locale": "<tag>"}` into
  every component (and a header-only glossary file) — the template for new translations. Translators cannot add
  languages (`new_lang: contact`); `en.arb` is not used as a template because its empty copies would hide the English
  fallback.

### 9.3 How a draft becomes a translation

```
Claude → i18n/<c>/drafts/<loc>.arb  (PR, merged)
  → python3 tools/i18n/weblate_import_drafts.py --apply     method=fuzzy ("needs editing"), conflicts=ignore
  → Weblate: needs editing → a translator edits / confirms → translated → a reviewer approves → approved
  → only approved strings are committed (commit policy) → squashed per language → pushed to weblate-translations
  → pull request → CI (§9.6) → the owner merges → i18n/<c>/<loc>.arb
  → node tools/i18n/prune_drafts.js --write   (a normal commit: drafts of approved keys removed, empty files deleted)
```

* The import sends only keys that are in `en.arb` and not yet approved in `<loc>.arb`; `conflicts=ignore` never
  overwrites a translation made in Weblate; `--skip-sensitive` leaves out `x-sensitive` keys (they need a reviewer
  anyway: check.js refuses a sensitive key that is only drafted in a locale that is on). The token comes from
  `WEBLATE_API_TOKEN` in the environment, never from a file; without `--apply` nothing is sent.
* `--method suggest` turns drafts into suggestions instead (for languages where a reviewer prefers to pick).
* Until a draft is approved, the runtime shows it only while the locale is `preview` (build.js: `d` beside `m`).
* After the merge, `prune_drafts.js` keeps only unreviewed keys in `drafts/`: a draft never goes back to Weblate once
  its key is approved, and the review queue stays honest. `--check` (CI warning) reports drafts that could be pruned.

### 9.4 The language-course facades

`facades/<locale>/*.json` (`{address: {t, src, by}}`) are not a Weblate format (three values per text; addresses
contain dots, which *JSON nested* would split). `tools/i18n/weblate_facades.py` converts them, per facade file, to
flat monolingual JSON (*JSON file*) on the exchange branch **`weblate-facades`** — derived data; `main` keeps the
facades as the single source of truth:

* `export <course> --out <worktree>/weblate-facades`: `en.json` = the master, keys **`<address>#<hash>`** (the hash
  is `src`: the first 12 hex digits of the SHA-256 of the English master text); `<locale>.json` = reviewed texts made
  for the current master; `drafts/<locale>.json` = `by: "claude"` texts and reviewed texts whose master changed
  (uploaded as *needs editing* by `weblate_import_drafts.py --facades`); `INDEX.json` = the components.
* A changed master text is a **new key** in Weblate (its translation memory offers the old translation), so every
  translation Weblate writes is bound to the exact master text it was approved against.
* `import <course> --from <worktree>/weblate-facades [--write]` (after merging Weblate's pull request
  `weblate-facades-translations → weblate-facades`): writes changed entries with `src` = the key's hash and
  `by: "weblate"`, never deletes, skips a translation of an older master text when the facade already has one for
  the current text, refreshes `facade.json` coverage. Requires the commit policy "only approved" (every string in a
  Weblate-written file is taken as approved). `lang_facade.py parity` then reports done / stale as before.

### 9.5 A locale's life: off → preview → on

1. **off** (`config.locales[<tag>]` absent or `'off'`): not offered. To start: `init-locale <tag> --write` (PR,
   merge), Weblate pulls and shows the language; Claude's drafts are imported (§9.3).
2. **preview** (`config.locales[<tag>] = 'preview'`, a PR to config.js by the owner): deploy previews show approved
   texts and drafts, so reviewers can check translations in context; the live site does not offer the locale.
3. **on** (`'on'`): only when Weblate shows the locale's components approved (and `node tools/i18n/check.js` passes
   with the locale on: every key translated or drafted, no sensitive key only drafted — the warning "draft(s) waiting
   for review" should be gone too). E-mails follow §6.4 (only fully translated templates). A facade's own status
   (`facade.json`: `draft | preview | on`) follows the same steps for the explanation language.

### 9.6 Checks in CI

`.github/workflows/i18n.yml` runs on every pull request that changes `i18n/`, `tools/i18n/`, the runtime or `weblate/`
— Weblate's pull requests above all: `node tools/i18n/check.js` (ICU syntax, placeholders equal to English, **every
CLDR plural category of the locale** — Weblate's ICU check validates syntax and placeholders, the per-language plural
categories are ours — apostrophes, sensitive keys, locales that are on), `node tests/i18n.js`, `prune_drafts.js
--check` (warning) and `python3 tests/weblate_tools.py` (the tools of this section, no network; it also belongs in `tests/run_e2e.sh`
next to `tests/i18n.js`). Protect `main` with "require a pull request" and the `i18n` check.

### 9.7 Contributor agreement (commercial use)

Translators must accept an agreement that grants the owner a perpetual, worldwide, royalty-free licence to use their
contributions **commercially** before they translate. `weblate/CLA.md` is a **DRAFT — must be reviewed by a lawyer

## 10. Subject packs in several languages

Approach 4 of §3: a pack's content is curated and written in **one** language (`subject.language`, its *speaker language*
in §1). The UI language never changes it by itself; a pack MAY offer translations of its metadata and (optionally) of its
chapters, and the learner sees them when the pack has their UI locale. The contract for authors is
`tools/CONTENT_SPEC.md` → "Packs in several languages" (also in the skill and the connector's `noema_authoring_guide`).

| | Source (subject folder) | Built pack (`pack.json`, schema v2) | Where it shows |
|---|---|---|---|
| Content language | `subject.language` (exists since v1; default `en`) | `subject.language` | the tag; the tutor replies in the content language |
| Metadata | `subject.json` → `i18n: { "<locale>": { title, appTitle, description, searchExamples, hero{…}, tutor{…} } }` | `subject.i18n` (also in the registry, in `a:packmeta:*`, in public packs' `meta.i18n`) | picker, Shelf, Explore, shared packs, the subject's home and page title |
| Content (optional) | `translations/<locale>/chNN.json` — the whole chapter, same ids and answers | `translations: { "<locale>": { chapters: [...] } }`; the registry / packmeta / public `meta` list them as `contentLocales` | the chapters, exercises, cards, playbooks |

* **Which version.** `packLocale()` (engine/loader.js) walks the UI locale's chain without the final English
  (`es-ES → es`; `zh-Hant` never `zh-Hans`): the first that is the pack's own language → the source texts; the first the
  pack offers → that translation; nothing → the source texts. An English learner never gets a translation "back" into
  English of a Greek pack unless the pack offers `en` and the UI is English.
* **Metadata and content are independent**: `subject.i18n.el` without `translations/el` gives a Greek name for English
  chapters. `Noema.subject` is the localized subject (`metaLocale`, `contentLang`; with a content translation also
  `language` = that locale and `sourceLanguage` = the pack's own); `window.COURSE` is `translatedChapters(pack, loc)`:
  chapter by chapter, a missing chapter (or one whose sections differ) stays in the source language, items a translation
  lacks (a later patch) are taken from the source — progress is keyed by ids and is shared between the versions.
* **The language tag** (`Noema.langTag(s)`, CSS `.noema-langtag`): the content language's code (e.g. `EN`), with
  `packs.langTag` (“Content in {lang}”, the language name from `NoemaI18n.fmt.langName`) as tooltip and label — shown only
  when the content language is not the UI language; never on language courses.
* **The learner's own name** (✏️ Edit subject, `a:subjoverride:*`) always wins over the pack's translations; saving the
  translated name unchanged stores no override.
* **Backward compatible**: `"v": 2` only for packs that use the fields; older apps ignore `subject.i18n` and
  `translations` and show the source texts; old packs need nothing. `tools/build.py`, `make_pack.py` (skill),
  `unpack.py` (back to `translations/`), `tools/validate.py --subject` / `--source` and `engine/packcheck.js` (the
  connector and the app) check them: locale codes (BCP 47; a warning for one no UI locale reaches), known fields, only

* Tests: `tests/validate_pack_i18n.py` (validator), `tests/pack_i18n.js` (picker, Shelf, Explore, home in en / el / fr / ru;

* Not yet: a per-subject switch “show the original” (today the UI language decides), translated `sources.json` titles and

## 11. Machine translation of shared content

Texts other learners wrote and shared — titles and descriptions in 🌍 Explore (subjects and Roadmaps), the title of a
Roadmap someone invites you to — stay in their author's language. `engine/mt.js` (`window.NoemaMT`, component
`i18n/mt/`, keys `mt.*`) translates them **on request** into the UI language, and the original is always one tap away.

**Providers — the learner's own keys only.** Claude (the API key on this device, `engine/claude.js` `Key`) or Gemini
(the device's Gemini key, `loader.js` `GeminiKey`), called from the browser through `engine/llm.js` (`NoemaLLM.json`, a
JSON answer `{ t: [...] }` checked for the right count). Nothing goes through a noema-lite server and there is no new
secret; the key the app may ship with (`DEFAULT_GEMINI_KEY`) does not count. No own key → nothing is translated: the
original stays, with the hint `mt.hint.nokey`. ⚙️ `a:settings.mt.provider`: `auto` (Claude when its key is set, else
Gemini) · `claude` · `gemini`. The prompt is English (approach 6) and tells the model that the texts are data, never
instructions.

**Consent.** Off by default (`a:settings.mt.on`, synced with the account). Me › Language & appearance has the section
*Machine translation* (`NoemaMT.panel`): the consent text (`mt.set.consent`, plain product text — what is sent, to whom,
what is kept on the device, what is never sent, that it may cost a little), the switch, the provider, the caps, *Clear
saved translations*. Asking to translate while it is off opens the same text as a dialog (*Turn on and translate* / *Cancel*).

**Policy check — before anything leaves the device** (`NoemaMT.check`). Only these kinds may be sent:
`explore.pack`, `explore.roadmap` (public listings), `shared.roadmap`, `shared.pack` (what was shared with the learner).
Never: any other kind (a private note, a person's message — the invitation's personal message is not offered), an item
marked `private` / `sensitive` / `visibility: 'private'` / `public: false`, a text that looks like personal data (an
e-mail address, a phone number of 9–15 digits that is not a date, an API key or token), an empty or very long text
(> 4 000 characters). Such items come back with their original and a `reason`.

**Language — cheaply.** `NoemaMT.detect(text, stored)`: the dominant script (Greek, Cyrillic, Arabic, Hebrew, Devanagari,
kana → ja, Han → zh, Hangul, Thai); for Latin script the stored `language` field (public packs and Roadmaps have one),
else a handful of function words (en fr de es it pt tr sq); unknown → no toggle. A toggle appears only when the language
differs from the UI locale (`zh-Hans` and `zh-Hant` count as one).

**Cache.** Per account on this device (`localStorage` `noema-device:mt:cache:<acc>`), keyed by a hash of the text and
the target locale; least recently used out above 3 000 entries or 250 000 characters. A cached text is shown again
without a request (also after a reload and in a redrawn list).

**Caps** (⚙️, per account): characters sent per day (`dailyChars`, default 20 000, counted on this device), requests
per session (`sessionRequests`, default 30, `sessionStorage`), and at most 6 requests a minute (`config.mtPerMinute`).
A text over a cap is not sent (`reason` `cap.daily` · `cap.session` · `cap.rate`, with a hint). Requests carry at most
40 texts / 8 000 characters each; identical texts are sent once.

**Cost estimate.** Before a bulk translation (more than one text not in the cache) the learner sees
`mt.estimate` — texts, characters, the price at list rates of the provider (`NoemaClaude.priceOf` of the chosen model,
or `config.geminiPrices`, default Flash) — and confirms.

**UI.**
* `NoemaMT.mark(node, { language, kind, private })` marks a node whose text is a shared text (its original is kept).
* `NoemaMT.toggle(acc, nodes)` → *🌐 Translate* / *🌐 Show original* for one item (null when nothing there needs it):
  the 🧭 Explore curricula cards (title + description), the info card of a 🌍 Explore subject, a Roadmap invitation (title).
* `NoemaMT.bar(acc, root)` → *🌐 Translate all* / *🌐 Show originals* for every marked text inside `root`: the 🌍 Explore
  dialog (`loader.js`), 🧭 Explore curricula (`curmap.js`) and the frame's Explore pages (`shell.js`); hidden while nothing
  needs a translation; texts drawn later (a search) take their cached translation while it is on.
* A translated text gets `data-mt-state="mt"`, `lang` = the UI locale, `dir="auto"`, a small *machine-translated* tag
  (`mt.badge`) and a tooltip with the original language, the provider and the original (`mt.badgeTip`); the bar adds
  `mt.note` (“may contain mistakes”). *Show original* restores the text exactly.

**API.** `NoemaMT.translate(texts, { from, to = UI locale, kind, acc })` → `[{ text, original, translated, cached,
provider?, reason? }]` (`texts`: strings or `{ text, language, kind, private, sensitive }`); it never throws for policy,
caps or a provider error (`reason: 'error'`, `.error`). `estimate(texts, { to, acc })`, `detect`, `differs`, `check`,
`provider(acc)`, `settings` / `setSettings`, `cache` (`get`, `put`, `size`, `clear`), `usage`, `useProvider(mock)` (tests).

**Tests.** `tests/mt.js` (mocked provider): own keys only, detection, the policy (private / sensitive / personal data never
reach the provider), cache hits and size cap, the three caps, the estimate, toggle, bar, consent, no key, the Greek UI.
